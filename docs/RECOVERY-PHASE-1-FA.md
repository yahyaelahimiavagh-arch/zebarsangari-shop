# زبرسنگری — مرحلهٔ اول پایداری و بازیابی (بدون تغییر دیتابیس)

## چه چیزی در کد اصلاح شده؟
- P1: در \`/api/products\` به‌جای کوئری با ۱۰۱ تا ۱۵۰ پارامتر، فراخوانی‌های D1 با حداکثر ۷۵ شناسه اجرا می‌شوند. این اصلاح تا سقف فعلی **۱۵۰ محصول** کاتالوگ را سالم نگه می‌دارد.
- این مرحله **صفحه‌بندی نامحدود** نیست: محصول ۱۵۱ به بعد هنوز به API عمومی نمی‌آید و باید در مرحلهٔ Pagination سمت سرور اصلاح شود.
- فایل‌های \`scripts/backup-cloudflare.mjs\` و \`scripts/verify-backup.mjs\` فقط ابزار آمادهٔ بکاپ هستند، **هنوز هیچ بکاپ واقعی گرفته نشده**.
- \`.gitignore\` جلوی اضافه‌شدن تصادفی پوشهٔ محلی \`private-backups/\` به مخزن عمومی را می‌گیرد.
- تست‌های کاتالوگ بدون وابستگی جدید و CI با Node 22 اضافه شده‌اند.

## تهیهٔ بکاپ واقعی D1 + KV در ویندوز/PowerShell
این مرحله روی کامپیوتر خودت انجام می‌شود، نه در GitHub Actions عمومی، نه روی وب‌سایت.
**اطلاعات مشتری، نشانی‌ها و احتمالاً رسیدهای قدیمی بانکی در خروجی هستند.**

۱. آخرین شاخه \`main\` را روی کامپیوتر دریافت کن و وارد ریشه پروژه شو. Node.js 22 نصب باشد.
۲. در Cloudflare یک API Token **محدود و فقط خواندنی** برای D1 و Workers KV بساز. توکن را در چت، اسکرین‌شات یا GitHub قرار نده.
۳. Account ID را از صفحه اصلی داشبورد Cloudflare بردار. شناسه KV از \`wrangler.jsonc\` خوانده می‌شود.
۴. در همان پنجرهٔ PowerShell، متغیرهای محیطی را به‌صورت محلی تنظیم کن:

\`\`\`powershell
$env:CF_ACCOUNT_ID = "<your-cloudflare-account-id>"
$env:CLOUDFLARE_API_TOKEN = "<read-only-api-token>"
node scripts/backup-cloudflare.mjs --dry-run
\`\`\`

در حالت Dry Run باید فقط توضیح «No network call or backup was created» دیده شود.

۵. **در ساعت کم‌ترافیک** اجرا کن؛ Export دیتابیس D1 ممکن است درخواست‌های دیگر به دیتابیس را موقتاً مسدود کند:

\`\`\`powershell
node scripts/backup-cloudflare.mjs
\`\`\`

۶. پوشه‌ای مثل \`private-backups/zebarsangari-2026-...\` ساخته می‌شود؛ سه جزء مهم دارد:
- \`database.sql\`: Schema و داده‌های D1
- \`kv/*.bin\`: فایل‌های KV، با نام هش‌شده
- \`manifest.json\`: نام کلیدها، اندازه و SHA-256 هر فایل

در پوشهٔ ناقص، \`INCOMPLETE.txt\` باقی می‌ماند. از بکاپ ناقص برای بازیابی استفاده نکن.

۷. ابزار راستی‌آزمایی را اجرا کن (مسیر واقعی پوشه را وارد کن):

\`\`\`powershell
node scripts/verify-backup.mjs "private-backups/zebarsangari-<timestamp>"
\`\`\`

۸. یک نسخه را روی دیسک/فضای رمزگذاری‌شدهٔ مستقل نگه دار. **هرگز خروجی بکاپ را در GitHub عمومی یا پیام‌رسان ارسال نکن.**

۹. توکن موقت را از همان نشست پاک کن:

\`\`\`powershell
Remove-Item Env:CLOUDFLARE_API_TOKEN -ErrorAction SilentlyContinue
\`\`\`

## Baseline اولیه Schema
جدول‌های اصلی \`products\`, \`product_variants\`, \`product_images\` در مایگریشن‌های فعلی مخزن تعریف نشده‌اند.
بعد از بکاپ موفق، خروجی فقط ساختار را با \`npx wrangler d1 export zebarsangari-db --remote --no-data --output=private-backups/schema-only.sql\` بگیر؛ **ساختار واقعی را قبل از تبدیل به \`migrations/0001_baseline.sql\` بازبینی کن**.

## کنترل بازیابی
راستی‌آزمایی SHA-256 **جای تست بازیابی نیست**. قبل از Migration سفارش‌ها لازم است SQL را در یک دیتابیس آزمایشی/محلی مجزا بازیابی و تعداد جدول‌ها، محصولات و سفارش‌ها را بررسی کنیم. هیچ دستور Restore روی دیتابیس تولیدی را بدون تأیید اجرا نکن.

## ادامهٔ بعدی (هنوز فعال نشده)
- ثبت سفارش Idempotent با شناسه درخواست یکتا
- رزرو اتمی موجودی و بازگشت رزرو با لغو/انقضا
- کنترل نسخهٔ ویرایشگر تا موجودی کهنه بازنویسی نشود
- صفحه‌بندی کاتالوگ برای بیش از ۱۵۰ محصول و سفارش‌ها برای بیش از ۸۰ سفارش
- اعلان فروشنده و پایش شکست پیام‌رسان

تا زمان رفع ایرادهای ثبت سفارش و تست عملی، فروش واقعی را فعال نکن.
